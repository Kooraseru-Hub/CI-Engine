# DevForum

Reusable Roblox DevForum native PNG uploads, SHA-256 cache checks, and existing public topic first-post publication with anonymous verification. The project owns Markdown, SVG rendering, benchmark logic, destination IDs and cache storage.

Node.js 24. `node post.cjs rehearse <config.json> <post.md>` validates the configured destination and authored native image inventory offline. `prepare <config.json>` reads the existing post and returns its digest and verified upload inventory. `publish <config.json> <post.md> <digest>` rejects concurrent changes and verifies saved public images. Use the `post` composite action with the corresponding mode. The config must contain `{"destination":{"topicId":42,"postId":7}}` (example IDs only).

`node upload.cjs <file.png>` computes a fingerprint without remote writes. Add `--publish` or use the `upload` action with `confirm: 'true'` to upload. The exported `cachedUpload` checks identical bytes and verified public availability before reuse.

Authenticated commands require `DEVFORUM_UPLOAD_KEY` and `DEVFORUM_UPLOAD_CLIENT` in a protected job. Credentials are only sent to the exact Roblox DevForum origin, never anonymous image storage. This package does not create topics or store cache data in CI-Packages. No external mutations in tests.

For recovery after an interrupted publication, `node post.cjs recover <config.json> <snapshot-sha256>` returns native upload references mapped to Git blob SHA-1 identities of the anonymously accessible original PNGs. Compare against regenerated bytes before adopting a reference. This operation is read-only; it never downloads optimized thumbnails or follows redirects.

## Release announcement drafts and delivery

`node announcement.cjs draft <owner/repo> <tag> <config.json> <output-directory>` reads an actual published non-prerelease release, resolves its tag to a commit, enumerates the existing public topic, and writes `announcement.md` and `announcement.json`. It does not use forum credentials, save a native composer draft, or make any external writes. The `announcement` action exposes the same read-only operation. The exact plan has a SHA-256 approval digest and a stable per-repository/topic/tag marker. A possible manually authored release reply with the same release link requires explicit adoption, not a second reply.

The exported `deliver` operation requires exact approval and a caller-supplied transport with an atomic, durable create-if-absent receipt reservation. It reconciles an existing marker, checks the author and post identity, rejects stale edits, reserves before creating, and never automatically repeats a failed creation. If the attempt is uncertain and the reply is not visible, it stops. The consumer must serialize sends per topic, persist receipts outside workflow history, verify the current release and destination, and reconcile unresolved reservations. The `deliver` action and `delivery.cjs <owner/repo> <tag> <config.json> <approved-sha256>` implement the receipt contract using GitHub Contents API on a caller-selected existing generated branch. Set `delivery.receiptBranch` and `delivery.receiptDirectory` in the project config. The caller must protect the job, supply Contents: write and forum credentials, serialize all writers of the generated branch, and retain the receipt directory during regeneration. Use the generated branch publisher's optional expected-heads guard to reject concurrent branch changes. A trusted default-branch manual dispatch, exact approval, current published release, authenticated topic author and atomic reservation are mandatory. A pending receipt is never automatically deleted or retried. Unit tests exercise the complete adapter with mocked writes and failure recovery; no live forum reply is created by CI.

`node post.cjs inspect <config.json>` is the anonymous read-only equivalent of the first-post preflight. It requires no DevForum credential.
